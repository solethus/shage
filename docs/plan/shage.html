The first half of this document argues for a semcode sidecar. That is still the right answer for breadth — C, C++, and the commit corpus. But for a Rust-first v1 it is the wrong starting point, because rust-analyzer already ships a scip subcommand that emits a compiler-grade index, and the scip crate reads it in Rust. What it costs you

The recommendation, stated plainly

Ship B first, behind an IndexBackend trait that mirrors the VcsBackend and ForgeBackend traits tuicr already has. That gets you a working "follow" in weeks instead of quarters, keeps tuicr installable by people who have never heard of semcode, and leaves C available later without touching a single call site. A is the option that looks cheapest on a whiteboard and is the one that will make you regret it — it drags libclang, protobuf, a C++ compiler and a second git implementation into a project whose headline feature is curl … | sh.

Exhibit A — where the two codebases disagree

Six axes. On five of them they were built for opposite worlds.

This is not a criticism of either project. tuicr is optimised for a 16-millisecond frame and a static binary; semcode is optimised for indexing the Linux kernel and answering questions about it. Both are right. They just cannot be the same process without one of them losing.

semcode

The one that actually blocks you

Not the runtime. Not git. It's SyntaxHighlighter. tuicr's own notes record that it is not Send, which is why every forge call already splits into "network on a background thread, parsing on the main thread". Any index integration inherits that rule: the background thread may return only plain data, and anything that touches highlighting or the App struct happens on the main thread when the channel is drained.

The one that looks scary and isn't

Licensing. tuicr is MIT; semcode is MIT OR Apache-2.0. You may take semcode under MIT and ship a combined MIT work. The only real obligation is attribution. Note that semcode also asks kernel-style DCO contributions to route through a separate repo — worth reading before you plan on upstreaming anything substantial.

Exhibit B — the integration seam already exists

You do not have to invent the concurrency model. tuicr wrote it for the forges.

Every GitHub and GitLab call in tuicr already follows one pattern: snapshot the inputs on the main thread, spawn a thread that returns only Send data, hand it back over an mpsc channel, drain the channel each tick, then parse and mutate state on the main thread. An index query is the same shape as a PR fetch. Click a module to see what it would look like.

The tool you want already ships, and nobody named it after code review

semcode's MCP server exposes diff_functions — "extract and list functions from a unified diff". That is not a search primitive, it is a review primitive: hand it the patch you are already looking at and it tells you which symbols the change touches. Paired with find_callers, that is the entire feature you described, and it is reachable today over stdio JSON-RPC without compiling anything into tuicr. Start there and measure before you write a line of index code.

Why leader shortcuts, not single keys

tuicr's contributor notes are explicit that single-stroke keys are reserved for vim motions, and that maintainers have refused to add them even for existing features. So every index binding hangs off the configurable leader (default ;) or a : command. Respecting that constraint is the difference between a patch that gets merged upstream and a fork you maintain forever — and it forces the good design anyway: the palette is the interface, the keybinding is only the shortcut.

The genuinely new idea

Neither tool does this today: order the file tree by blast radius instead of by path. A three-line change to a function with 200 callers deserves your attention before a 300-line change to a test helper. The index already knows the caller counts; the review tool already owns the file list. Joining those two facts is a handful of lines and is the single most defensible reason to do this work at all.

The failure mode to design for on day one

The index is stale by construction. It was built at some commit; the reviewer is looking at a diff that may be newer, a PR from a fork, or uncommitted working-tree changes. semcode's working-directory overlay covers the local case — it stat-checks the git index and re-parses modified tracked files, roughly half a second across a 93,000-file kernel tree — but a GitHub PR you have never fetched is simply not in the database. Every panel needs an honest empty state that says which commit answered this, not a blank list that reads as "no callers".

Exhibit D — the part that is actually hard

Adding grammars is a weekend. Making the call graph true in Go and TypeScript is the project.

semcode stores functions.calls as a JSON array of function names. That is a sound model for C, where the namespace is flat and a name is very nearly an identity. It is not a sound model for a language with methods, interfaces, modules or aliases. Pick a rung and watch what happens to the same two snippets.

Where to stop

Level 1 is the sweet spot for review. It needs no compiler, no go.mod resolution, no tsconfig, and it stays incremental and fast enough to run on a laptop while you read a diff. It gets import aliases, arrow-function bindings, method receivers and package qualification right, which is most of what a reviewer actually asks. It cannot resolve interface dispatch, and it should say so rather than guess.

Where to cheat

Treat SCIP as an optional overlay, not a rewrite. scip-go and scip-typescript are compiler-backed and already exist; SCIP ships official Rust bindings, so a Rust tool can read an index.scip directly. If a repo has one — many already generate them in CI — load it and upgrade the affected edges from heuristic to exact. If it doesn't, fall back to Level 1. Same UI, better badges.

Per-language reckoning

What breaks when you leave C

The grammar crates are the easy half: tree-sitter-go and tree-sitter-typescript both depend on the tree-sitter-language shim, so they drop into semcode's tree-sitter 0.26 without a version fight. The extraction rules are the other half, and they are not portable.

"Macros" does not generalise, and neither does the table it lives in

semcode's entity model is functions (which also holds function-like macros), types, and typedefs — a C ontology. Go has no macros; its closest analogues are build tags, go:generate and cgo. TypeScript has none either, but it has type aliases, enums, decorators and ambient declarations that have no C counterpart. Before you add a second language, the entity model has to become Entity { kind, lang } with a per-language kind vocabulary. Doing that after Go is in the database means a migration on a store that is already measured in gigabytes — and semcode's own release notes show schema changes there force a full reindex.

The data model delta

One column has to change, and it changes everything downstream

Today a function record carries calls: a JSON array of names, indexed with a BTree so calls LIKE '%"malloc"%' is fast. That single design choice is what makes semcode quick, and it is also what caps it at Level 0. Making it language-honest means storing call sites and resolving them separately.

The query worth writing first

Given the hunks tuicr is already displaying, ask the index for the symbols in the patch, then for each symbol ask for its last five commits. Render them inline above the hunk. That is archaeology at the point of decision: the reviewer sees "this line was last touched by the commit that fixed a race, six weeks ago" without leaving the diff. It needs one new MCP round trip, no schema change, and it is the feature people will actually talk about.

What will actually bite

Ranked by how likely it is to stall the work

None of these are reasons not to do it. All of them are reasons to keep the boundary thin.

Highest

Both upstreams move fast

tuicr has shipped more than twenty-five releases and is actively restructuring internals; semcode's own release notes repeatedly say a change is a schema change and you must reindex. Any deep fork of either goes stale in a quarter. A trait plus a process boundary is the only version of this that survives contact with both roadmaps.

Highest

semcode is aimed at the kernel

Its recent features are lore.kernel.org mailing-list indexing, kernel patch-review prompts and DCO contribution routing. That is a healthy, specific product direction — it is just not "Go and TypeScript monorepos". Do not assume the language work lands upstream on your timetable; plan to write and own it, and offer it back.

High

Index staleness reads as absence

An empty caller list means either "nothing calls this" or "the index has never seen this commit", and those are opposite conclusions for a reviewer. Every panel must carry the commit stamp and an explicit empty state. Get this wrong and people stop trusting the feature within a week.

High

False edges are worse than none

A name-matched graph on Go will confidently link every Close to every other Close. The reviewer approves a change believing they have seen the blast radius. Confidence badges are not polish here, they are the safety mechanism.

Moderate

Build and distribution

semcode wants a C++ compiler, libclang and protobuf to build. tuicr ships prebuilt binaries via a one-line installer and its notes are explicit that static glibc builds have crashed on hostname lookup, so musl is the supported static target. Fusing the build systems means owning that intersection on every platform you ship.

Moderate

Latency inside a frame

A TUI redraws in milliseconds; a cold LanceDB call chain does not. The mpsc pattern keeps the UI responsive, but you still need a spinner state, a cancel path when the cursor moves, and stale-result discard keyed on the request identity — the same discipline tuicr already applies to in-flight PR fetches.

Moderate

Two git implementations

git2 links libgit2; gix is pure Rust and semcode's conventions forbid shelling out to git at all. They coexist in a dependency tree without fighting, but in one binary you are paying for two object-store readers and reconciling two notions of a repository. Another argument for the process boundary.

Low

Disk footprint per repo

The index lives beside the source as .semcode.db, with sixteen content shards, BTree indices on almost every column and optional vector tables. Fine on a workstation, awkward on a laptop with twelve checkouts, hostile in CI. Decide early whether the index is a per-checkout artifact or a shared service.

Sequencing — each phase ends in something usable

Measure first. Language work is phase three, not phase one.

The temptation is to start with Go and TypeScript because that is the exciting part. Don't. Prove the seam on the languages semcode already parses, where a wrong answer is obvious, and only then take on resolution.

Part II — building it

The version you can start on Monday, in Rust, with no index server.

The tool is called shage. Earlier drafts used cairn, which turned out to be taken — a reminder that the name check belongs at the top of the fork checklist, not the bottom. Everything below is written against shage: the crate names, the binary, the config paths, the ignore file and the prompts. One thing left to do before the first cargo publish: a crate name is claimed permanently by whoever publishes first, so run cargo search shage and command -v shage now, and consider publishing a 0.0.0 placeholder to reserve it while you build.

The unlock — you already own a compiler-grade indexer

rust-analyzer emits SCIP. That is the whole v1.

Nothing in Part I is wrong, but it buried the lede for a Rust-first build. rust-analyzer scip . runs batch analysis over a cargo workspace and writes index.scip: definitions, references, implementations, hover docs and cross-crate monikers, all from the same engine your editor already trusts. The scip crate on crates.io reads it. You get level 3 on the ladder without writing a resolver, running a database, or shipping a second binary.

use scip::types::{Index, SymbolRole}; /// SCIP is protobuf. Reading it is not the hard part. pub fn load(path: &Path) -> Result<Index> { let bytes = fs::read(path)?; Ok(Index::parse_from_bytes(&bytes)?) } /// The hard part is this: SCIP gives you occurrences, not /// edges. A "caller" is a reference occurrence, resolved to /// whichever definition's range encloses it. pub fn referrers(ix: &Index, sym: &str) -> Vec<SymbolRef> { ix.documents.iter().flat_map(|doc| { let tree = EnclosingTree::build(doc); // interval tree doc.occurrences.iter() .filter(|o| o.symbol == sym) .filter(|o| !has_role(o, SymbolRole::Definition)) .filter_map(|o| tree.enclosing(o.range())) .collect::<Vec<_>>() }).collect() }

Be precise with the word "caller", or you will ship a lie

SCIP records occurrences, not call edges. A reference to Bucket::allow might be a call, a function pointer, a trait bound, a use statement or a doc link. If you label all of those "callers", a reviewer will over-trust the count. The honest v1 architecture is a hybrid: SCIP decides identity — which symbol this token really is, across crates, through aliases and re-exports — and tree-sitter classifies the site — is this token in call position, type position, or an import. Two cheap passes, and the badge on each row tells the truth. This is the single most important implementation detail in Part II.

The strategic shape this gives you

One trait, three tiers, and each tier is someone else's maintained software. Tier 1 is SCIP: borrow six compilers' worth of correctness for the price of a protobuf parser. Tier 2 is your own tree-sitter pass for repos that won't build. Tier 3 is semcode for breadth and git archaeology. You write the review-specific layer — blast radius, ranking, freshness, the panel — and almost none of the language work. There is even prior art for orchestrating the indexers: scip-io detects languages, installs the right indexer and merges per-language indexes into one file, in Rust.

Fork mechanics — how to leave without burning the bridge

Fork it, rename it, and keep the rebase cheap forever

tuicr ships more than twenty-five releases and is still restructuring internals. A fork that edits fifty of its files is dead within a quarter. A fork that edits six, all of them at named hook points listed in a file that CI enforces, can rebase weekly for years. The discipline is not "don't fork" — it is bound the diff and write it down.

Three ways to ship this

Upstream PR. Best outcome, slowest, and you do not control the roadmap. Worth attempting for the IndexBackend trait alone, once it has proven itself.

Companion binary. tuicr already exposes a library API and a JSON-emitting review CLI, so a sidecar tool can read sessions and add comments today, with no fork at all. But the follow panel has to render inside the TUI, so this can only ever be half the product.

Bounded fork. What is described here. Take the fork, but treat upstream as a vendored dependency you happen to be able to patch.

day one — set the remotes up so drift is visible
gh repo fork agavra/tuicr --clone --fork-name shage cd shage git remote add upstream https://github.com/agavra/tuicr.git git fetch upstream --tags git checkout -b main upstream/main # start clean at a tag git tag vendor/tuicr-v0.19.0 # the point you diverged # restructure into a workspace BEFORE writing any feature mkdir -p crates/shage-core git mv src Cargo.toml crates/shage-core/ # root Cargo.toml becomes [workspace] # weekly, forever: git fetch upstream git rebase upstream/main # conflicts only in shage-core cargo xtask seams --check # fails on undeclared drift

The one rule that makes the whole thing work

Every new line of code you write lives in a crate upstream has never heard of. crates/shage-index and crates/shage-follow are yours entirely; crates/shage-core is the fork and is touched only at declared hook points. Six edits: the event loop gains one poll call, App gains four fields, the Action enum gains six variants, InputMode gains one, the annotation enum gains one variant, and the renderer gains one match arm. Write them down in docs/SEAMS.md and make cargo xtask seams --check fail the build when a seventh appears. Fork drift becomes a thing you notice on the day it happens, not the day you try to rebase.

Repository shape — optimised for a reader with no memory

Structure it so an agent can be useful after reading one directory

Layer-first layouts (models/, services/, utils/) force a reader to hold the whole repo in mind to change one thing. Domain-first layouts do not. The test that matters: can someone who has read exactly one folder and one contract file ship a correct change? Click through the tree.

The seven rules, and why each one exists

RuleWhat it prevents
One slice, one directory, one AGENTS.mdAn agent asked to change caller derivation reads callgraph/AGENTS.md and contract.rs, and nothing else. Context stays small, so the answer stays accurate. A root-level AGENTS.md that documents everything gets skimmed and half-applied.
Cross-slice traffic goes through contract.rsSlices importing each other's internals is how a codebase becomes unsplittable. If a slice needs a new shared type, that is a contract change and gets its own small pull request — which makes the coupling visible instead of accidental.
Files stay under about 400 linesNot aesthetics: an agent that has to read a 2,000-line file to change 5 lines will paraphrase the rest and quietly reintroduce a bug you already fixed. Split by behaviour, never into a helpers.rs.
No utils, common, shared or miscThose names mean "I did not know where this goes". They become the place everything lands, and then nothing can be reasoned about locally. If you cannot name a directory after a domain concept, you have not found the concept yet.

The prompt library — version it with the code

Nine prompts. Keep them in docs/prompts/ and treat them as source.

A prompt that lives in someone's clipboard history is not a process. These are written to be checked in, edited when they produce a bad result, and reviewed like code. The shape is deliberate and consistent: read first bounds the context, constraints and do not carry more weight than the task, and done when is a command that either exits zero or does not. Angle brackets are the only things you fill in.

Why "read first" is the load-bearing section

An agent given a whole repository will read broadly and shallowly, then write something that is locally plausible and globally wrong. An agent pointed at one slice's AGENTS.md and one contract.rs has enough to be correct and not enough to improvise. The structure in the previous section exists to make that instruction possible — the repo layout and the prompt library are the same design decision.

The instruction people leave out

"If the spec is wrong, stop and tell me." Without it you get a confident implementation of a misunderstanding, and you find out three slices later. With it you get a question you can answer in thirty seconds. Every implement-shaped prompt here has a version of that line, and it is worth more than all the formatting rules combined.

Close the loop with the tool you are building

tuicr already ships an agent skill: the agent opens the TUI in a split pane, you review, and it reads your comments back as structured JSON through tuicr review comments. Fork that skill on day one. From then on every prompt above ends the same way — the agent writes the change, opens shage in a pane, waits, and picks up your inline comments as its next instruction. You are dogfooding the review tool while building the review tool, which means a bad panel gets fixed the same afternoon you notice it.

Testing — three layers, one of them unusual

Let the compiler grade your heuristics

The interesting test problem here is not the TUI, it is correctness of resolution — and resolution is exactly the thing that is hard to write assertions for by hand. The way out is that you already have a compiler-grade answer sitting in index.scip. Use tier 3 as the oracle for tier 1. Your heuristic resolver is graded against rust-analyzer on generated fixtures, automatically, on every pull request.

The fixture rule worth writing on the wall

Generate fixtures from code; never commit a .scip file or a tarball of a repo. A committed binary fixture silently drifts from the real encoding as the indexer version moves, and then your tests are asserting against a museum piece while production reads something else. The generator script is the fixture. It is also the only readable description of what each hazard actually is.

Execution — the first ten pull requests

Each one small enough to review in ten minutes

Sequenced so that every step is independently useful and independently revertible. The prompt named on each is from the library above. Nothing here needs a second process, a database, or a language you cannot already index.

Where the fork stops being a fork

Somewhere around PR 7 you will have something upstream might genuinely want: a backend trait, a panel, and a demonstration that it does not regress anyone who never installs an indexer. That is the moment to open the conversation — not at PR 1 with a plan, and not at PR 30 with fifteen thousand lines. Offer the trait and the null backend first, keep the SCIP implementation in your crate, and let the maintainer decide how much surface they want. Whatever they say, the bounded-fork structure means the answer costs you nothing either way.

Part III — the layer you build once the core works

Themes, overlays, and the palette: cheap to add, ruinous to retrofit

This is explicitly post-core work — none of it makes a review more correct. But two of the decisions here are load-bearing and near-impossible to reverse: whether colours are named semantically or literally, and whether overlays share one stack. Get those two right in the first week of UI work and everything else is additive. Get them wrong and you repaint every widget by hand for the rest of the project.

Copy the design, not the bug

opencode's theme loader has shipped crashes when a theme used ANSI integer indices — a type confusion in colour resolution that took the whole TUI down at switch time. The lesson is structural, not incidental: a theme is untrusted user input, and it arrives from a file the user edited by hand at the exact moment they are watching. Parse it into a fully-resolved Theme struct before swapping the active one, validate every role is present, reject with a message in the status bar, and keep the previous theme live. A bad hex string should be a one-line complaint, never a stack trace where the diff used to be.

What not to build

Skip

Mouse-first anything

Upstream supports mouse and that is enough. Building drag-to-select or clickable gutters means maintaining two interaction models, and the people who install a vim-keybound review TUI are not the people asking for it.

Skip

Animation

A spinner while a query is in flight, and nothing else. Transitions in a terminal are a redraw storm on a slow SSH link, and they age badly. Motion should mean "something is happening", never "this looks nice".

Skip

Image and graphics protocols

Sixel and kitty graphics are tempting for a call-graph picture. They work in perhaps a third of terminals, degrade to garbage in the rest, and a call graph rendered as a picture is less useful than a ranked list you can jump from.

Refuse

A second config format

Upstream config is TOML. Themes are JSON because that is what every editor's theme ecosystem already speaks and what makes porting a theme a copy-paste. Two formats, deliberately, for two audiences. A third is how you end up with settings nobody can find.

Refuse

Theme-specific layout

A theme sets colours. The moment one can change padding, borders or which panes exist, every layout bug becomes theme-dependent and your snapshot tests multiply by the number of themes.

Refuse

Colour as the only signal

Confidence badges carry a word, not just a hue. Blast radius shows a number. Roughly one reviewer in twelve cannot reliably separate your red from your green, and terminals let users override the palette anyway — so a design that leans on hue alone is broken for a slice of your users and for anyone running a light theme in a dark room.

The sequencing that keeps this honest

Ship the command palette and the registry during the core work, not after — because the registry is what stops keybindings from sprawling, and it is far cheaper to add before there are twenty of them than after. Everything else in this section waits until someone has actually reviewed a real pull request in shage and told you what was annoying. A theme picker on a tool nobody uses yet is procrastination with good taste.
